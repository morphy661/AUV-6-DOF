# AI在线诊断与规则FTC融合：第二阶段（2026-09-07）

## 结论与当前入口

已经实现在线模型→规则证据验证→FTC决策→下一步控制的真实接入路径。
融合模式通过 `--diagnosis-mode fusion` 启用，影子模式仍为默认值。

本轮功能检查通过，控制效果优于基线的证据尚未建立，完整任务安全验收未通过。
四个正常场景没有新增FTC介入，但V1完全失效后的持续航行/转向发生严重姿态失稳，
规则基线和融合模式都存在这个问题。不能将“没有新增误动作”写成“所有故障安全通过”。

## 执行时序

每个仿真步依次完成：

1. 使用上一时刻FTC决定的控制量推进运动，取得当前传感器和ESC数据。
2. 构建当前物理证据，包括ESC可信度、推力分配残差、控制饱和度和传感器保护状态。
3. 在线模型读取当前及过去数据，生成概率和时序诊断。
4. `AIControlEvidenceGate`验证模型证据，生成可追踪的规则判定。
5. FTC监督器只更新一次，融合后的决策从下一仿真步起作用。

日志中同时保存 `maintenance_diagnosis`、`ai_ftc_fusion`、`ftc_evidence_source`、
`ftc_action`和`ftc_applied_action`。采纳AI时证据来源包含`validated_online_ai`。
模型预测位置不进入隔离指令，H1–H4/V1–V2精确隔离仍只来自直接电流/RPM证据。

## 融合门槛

- 当前模型窗口可用，未被上下文门控抑制，传感器/ESC没有相关可信度保护状态。
- 推理时刻不在未来，结果年龄不超过0.60秒（默认0.05秒采样、每10步推理）。
- 采用冻结时序策略的0.85阈值，但这里要求具体故障模式的原始概率达到阈值，
  同时与时序层确认模式一致；这比只检查合计故障概率更严格。
- 至少两次不同推理时刻连续确认；重复展示/重复提交同一概率不累计确认次数。
- 当前饱和度≥0.80，并且轨迹误差比≥0.60或分配残差比≥0.15，才加入可供FTC使用的故障证据。
- FTC仍使用原有持续性计时、恢复观察和动作优先级。AI证据通过不等于立刻改变控制动作。
- 直接ESC硬故障和传感器保护不等待AI许可。

上述0.85来自已有冻结策略，0.80/0.60/0.15来自已有FTC配置；两次确认和结果保鲜是本轮新增的工程约束。
这些门槛尚未经过独立融合策略优化。概率不是已经校准的实际正确率，规则通过也不等于100%真实故障。
控制压力与模型输入可能相关，不能将二者当作统计独立的两次观测相乘计算置信度。

| 规则判定 | 含义 | AI是否增加FTC证据 |
|---|---|---|
| unavailable / context_blocked | 窗口未准备好，或上下文不可信 | 否 |
| stale_or_future_result / invalid_result | 时间或概率格式无效 | 否 |
| suspected | 等待时序确认或第二次有效推理 | 否 |
| probability_conflict / recovering | 新概率不支持锁定模式，或正在恢复 | 否 |
| record_only | AI持续提示异常，但控制压力不足 | 否，仅保留诊断记录 |
| accepted_control_evidence | 持续模型证据与可用控制压力相符 | 是，由FTC决定动作 |
| direct_rule_priority | 有直接ESC故障证据 | 直接规则走自己的确认通道 |

## 发现并显式标出的缺失信号

原证据接口读取 `tracking_error_ratio`，但当前仿真没有填入该归一化量，因此此前一直使用默认0。
本轮没有把真实仿真轨迹误差偷接进诊断，也没有任意设定位置误差的安全尺度。
新增 `tracking_error_available` / `ftc_tracking_error_ratio_available`，缺失时标为false，
统计报告将其显示为null；融合门控与FTC压力判断都不会将不可用轨迹量当作有效证据。

因此本轮真实模型试验实际使用的控制支持是“饱和度＋推力分配残差”。
轨迹误差分支由显式提供该量的接口测试覆盖，但未在这些仿真任务中得到真实运行验证。
后续应基于艇载估计值、任务跟踪允许偏差和状态可信度设计这个量，并对纯规则/融合两组同时接入，
避免把基础信号修复的收益误归因给AI。

## 成对仿真设计

十个场景，每个场景分别运行规则、在线影子、在线融合三组；每组40秒、0.05秒步长，
共30条轨迹、24000个仿真步，其中融合模式8000步。
模型为V3.5 seed43，权重和时序配置未重新训练或调参。

前九个场景的目标水平速度1.35 m/s，目标下潜速度0.10 m/s；12–20秒期间目标航向从0平滑变化到0.8 rad
（45.84°），保持其他目标姿态分量为0。故障在10秒开始，推力损失场景效率为35%（损失65%）。
外部扰动测试在8–14秒叠加[35,15,3,0,0,0.5]的艇体系力/力矩，是明确设定的压力测试，非实海标定数据。
最后一个场景复用seed20260911的200米多故障演示，含传感器、ESC通信和V2推力损失。

四个正常场景共304次原始模型推理，有12次argmax为故障类别，最终没有新增FTC介入。
这只说明本轮门控阻止了这些模型输出变成额外控制动作，不能宣称模型原始误报已经消失，
也不是新的独立盲测误报率。正常扰动场景仍有10步record_only，应理解为可能异常记录，不能当成已证实故障。

V1无输出场景：规则在10.55秒隔离V1；首次采纳AI证据为11.95秒，共39步。
但最终动作仍为目标推进器重分配，没有产生与基线不同的保护动作，且出现接近89°的俯仰。
这里的欧拉角接近奇异姿态，不能仅按横滚数字解释完整翻转过程；大俯仰本身已经说明姿态控制不安全。
H1推力损失场景也有明显航向偏离，不能因只记录了故障就视为运动控制合格。

## 验证范围与文件

250项回归测试通过，另有5项子测试通过。
新增边界测试覆盖过期/未来概率、重复结果、恢复状态、概率冲突、不可用轨迹误差、
传感器保护、AI不能隔离推进器，以及FTC只更新一次和下一步生效。
使用人工构造的诊断输出测试证明“有效AI＋控制压力”能够改变FTC决策；
这项测试验证接线和逻辑，不能冒充真实V3.5模型提高控制性能的证据。

真实模型十组对照中：影子与规则的轨迹/控制一致；融合日志在其自身轨迹上的因果回放概率一致；
每个控制动作满足下一步应用关系；没有新增误隔离。十个场景的实际控制轨迹均未相对基线改变。
所有结果位于 `math-model/results/six_dof_online_fusion_stage2_20260907/`，
包括 `fusion_validation_summary.json`、逐场景metrics.json和逐步fusion_trace.jsonl。

## 运行方法

在项目根目录生成融合模式演示：

```powershell
& 'D:/Anaconda_envs/envs/auv_gpu/python.exe' -B math-model/examples/demo_six_dof_unified_diagnostics.py --diagnosis-mode fusion --duration 30 --dt 0.05 --seed 20260911 --injection-mode random --model-device cuda --output-dir math-model/results/six_dof_online_fusion_demo_20260907
```

只需图表、JSON和日志时增加 `--skip-video`。视频FTC区域会显示当前AI与规则判定，
完整概率和验证理由位于 `online_model_trace.jsonl`。
`--diagnosis-mode shadow`运行第一阶段影子模式；`--disable-model`运行规则基线。

复现成对验证：

```powershell
& 'D:/Anaconda_envs/envs/auv_gpu/python.exe' -B math-model/examples/validate_six_dof_online_fusion.py --device cuda --output-dir math-model/results/six_dof_online_fusion_recheck
```

## 下一步优先级

优先补齐可观测的轨迹/姿态安全证据和故障后的任务降级约束，重点使用本轮V1完全失效反例。
需要明确剩余推进器是否能保持姿态、何时降低水平航速/暂停转向，以及安全保持或独立上浮请求的适用条件。
将这些基础修复同时应用到规则组和融合组后，再衡量AI是否改善检测延迟、误介入或安全恢复。
当前不应通过放宽AI阈值来强行制造与基线不同的FTC动作。
